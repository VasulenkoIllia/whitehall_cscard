# Ранбук: перенос PROD і TEST на новий сервер (15.08.2026)

Обидва середовища перенесені зі старого сервера `WorkfloMain` (`49.12.219.133`)
на новий (`77.42.87.94`, SSH на порту 2222) у ніч з 14 на 15 серпня 2026.
TEST переносили першим, PROD — після того, як TEST відпрацював реальне
навантаження.

| | TEST | PROD |
|---|---|---|
| Гілка | `develop` | `main` |
| Новий домен | https://systemtest.whitehall.store | https://system.whitehall.store |

Зменшення розміру бази — не втрата даних, а відсутність роздуття: `pg_restore`
будує індекси з нуля і не переносить мертві версії рядків MVCC.

## Цільова інфраструктура

Описана в [`DEPLOYMENT.md`](./DEPLOYMENT.md) — сервер, Traefik, Cloudflare,
`.env`, sparse-checkout. Тут лише те, що стосується самого переносу.

## Порядок дій (той самий для обох середовищ)

1. **Прибрати `.env` з версіонування.** Файл лежав у публічному репозиторії.
   Коміт `be11318`, окремо на обох гілках. Перед цим на сервері знято бекапи.
2. **Параметризувати compose.** Середовище-залежні поля (імена контейнерів,
   порт БД, домен, ім'я роутера) винесені у змінні з дефолтами — коміт `be70f3f`.
   Після цього `docker-compose.yml` однаковий на `main` і `develop`.
3. **DNS.** Записи `system` і `systemtest` у зоні `whitehall.store` (Cloudflare).
4. **Клон із sparse-checkout** — без `docs/`, `.claude/`, `.idea/`, `output/`.
5. **`.env` на новий сервер** + блок середовища + **новий пароль БД**
   (це параметр бази, яка ще не існує, а не ротація секретів).
6. **Дамп → перенос → restore.**
7. **Збірка образу наперед** (`docker compose build app`) — виносить хвилини
   збірки за межі вікна простою.
8. **Звірка** і лише потім запуск `app`.

### Крок 6 у деталях

```bash
# СТАРИЙ сервер: точні count(*) по всіх таблицях — еталон для звірки
docker compose exec -T db psql -U whitehall_store -d whitehall_store -At -F= -c \
"SELECT table_name, (xpath('/row/c/text()', query_to_xml(format('SELECT count(*) AS c FROM %I.%I', table_schema, table_name), false, true, '')))[1]::text::bigint
   FROM information_schema.tables
  WHERE table_schema='public' AND table_type='BASE TABLE'
  ORDER BY table_name;" | tee ~/counts-before.txt

# СТАРИЙ сервер: дамп
docker compose exec -T db pg_dump -U whitehall_store -Fc whitehall_store > ~/migration.dump
sha256sum ~/migration.dump

# Перенос через локальну машину (прямого каналу між серверами немає)
scp workflo@49.12.219.133:~/migration.dump /tmp/
scp -P 2222 /tmp/migration.dump root@77.42.87.94:/root/

# НОВИЙ сервер: звірити sha256, потім restore у порожню базу
docker cp /root/migration.dump <db-container>:/tmp/
docker exec <db-container> pg_restore -U whitehall_store -d whitehall_store \
  -j 4 --no-owner /tmp/migration.dump

# НОВИЙ сервер: той самий запит + побайтовий diff з еталоном
diff counts-before.txt counts-after.txt
```

Звірка саме через **точні `count(*)`**, а не `n_live_tup` з `pg_stat_user_tables`:
останній дає оцінку і розходиться з фактом на десятки рядків.

## Виміряні тривалості (PROD, 948 MB / 29.8 млн рядків)

| Етап | Час |
|---|---|
| Підрахунок `count(*)` перед дампом | ~1 хв |
| `pg_dump -Fc` | 2 хв 56 с |
| Перенос через Mac (вниз 7.5 MB/s, вгору 26.5 MB/s) | ~2.5 хв |
| `pg_restore -j 4` | **4.5 хв** |
| Звірка + старт `app` | ~2 хв |

`pg_restore` виявився вчетверо швидшим за початкову оцінку в 10–20 хвилин.

## Рішення, ухвалені під час переносу

- **Переносити базу цілком**, разом із `products_raw` (7.6 GB з 9.2 GB —
  проміжні дані імпорту). Вибіркове виключення таблиць приймається в момент
  найбільшої напруги і перевіряється найгірше. Задача `cleanup` о 04:00 сама
  підрізає партиції за ретеншеном (`CLEANUP_RETENTION_DAYS=10`) — наступної
  ночі найстаріша партиція відпала штатно.
- **Старий PROD зупиняти ДО зняття дампа**, а не після. Ключі не ротовані,
  тож два інстанси з одним CS-Cart API-юзером і одним Telegram-ботом не
  мають перетинатись ні на секунду.
- **Ключі не ротувати під час переносу** — рішення власника: спершу переїхати,
  ротація окремим кроком. Див. «Відкладені борги».
- **`AUTH_SESSION_SECRET`**: ротовано на TEST, **не чіпано на PROD** — щоб
  паролі й сесії користувачів лишились робочими без переналаштування.
- **`BUYER_PRICE_STATUS_TAB` і `CSCART_COLLECTION_FEATURE_ID` не прописувати
  явно.** Обох немає в PROD `.env`, застосунок бере дефолти `Оновлено` і `558`.
  Вписування кириличної назви вкладки вручну ризикує підмінити символ
  (`О` проти `O`) — тоді експорт створить **другу вкладку** в бойовій таблиці
  покупців. Виграшу нуль, ризик реальний.
- **Старі домени не переводити** на новий сервер: згаснуть разом зі старим
  сервером, відкат лишається чистим.

## Чищення мертвих таблиць (тільки TEST)

На TEST лишались 10 таблиць від відкоченої фічі AI Mapping Wizard
(міграції `042`–`052`, видалені комітом `2cf56bb`). Перед видаленням
перевірено: **0** згадок у зібраному коді (`/app/dist`, `/app/public`,
`/app/migrations`), **0** зовнішніх FK, **0** view. Знято окремий бекап,
далі `DROP TABLE ... CASCADE` в одній транзакції + прибрано 18 сирітських
записів із `migration_history` (40 → 23, рівно стільки ж файлів у репо).

PROD цього не потребував — там міграцій 17 і жодної сироти.

## Пастки, на які варто зважати

- **Шляхи проєктів на обох серверах ідентичні.** Команда
  `cd /var/www/projects/whitehall_cscard_test && docker compose stop`,
  призначена для старого сервера, була виконана на новому. Наслідків не було
  (штатна зупинка, `ExitCode 0`), але з тих пір усі команди для старого
  сервера даються із запобіжником по `hostname`.
- **Пайплайн може ще виконуватись, коли здається, що вже ні.** Перевірка перед
  зупинкою PROD показала `update_pipeline` у стані `running` на 22-й хвилині —
  тік о 00:00 ще не завершився. Прогін триває 25–30 хвилин, тобто «наступний
  тік через 2.5 години» не означає, що зараз тихо. Завжди дивитись
  `jobs WHERE status IN ('running','pending','queued')`.
- **`docker compose up -d --build app` перестворює і `db`.** Дані на bind-mount
  переживають це без втрат, але перевірити після перезбірки варто.
- **Застосунок не логує HTTP-запити**, тож із боку сервера не видно, які
  сторінки відкривались і чи віддали дані. Прийняття інтерфейсу — тільки очима.

## Перевірка після переносу

Перший нічний цикл на новому PROD (15.08.2026):

```
03:00  update_pipeline   28:21  success   (mirror 18:26 → import 08:57 →
                                           finalize 09s → price 01:20 → store 48s)
04:00  cleanup            0.2s  success   (партицію products_raw_20260804 знято)
06:00  update_pipeline   29:13  success
```

Тривалості збігаються з історичними зі старого сервера (25–30 хв) — новий
сервер не повільніший. Помилок рівня `error` — нуль. Попередження
`Import skipped rows` (причина `zero_quantity`) — ~110 на один імпорт проти
~103 на старому сервері, тобто та сама величина.

## Відкладені борги

1. **Ротація ключів.** У публічній історії репозиторію лишились робочі
   CS-Cart API key, Google private key і Telegram bot token. Порядок без
   простою: Google — другий ключ до того самого service account (обидва
   валідні одночасно), CS-Cart — окремий API-юзер, Telegram — revoke в момент
   перемикання.
2. **Регулярні бекапи.** На новому сервері їх **немає**. Є лише разові дампи
   з переносу в `/root/*.dump`. Потрібен `pg_dump` за розкладом + ротація +
   копія поза сервером.
3. **Гасіння старого сервера** — після того, як накопичиться статистика
   нормальних прогонів на новому.
