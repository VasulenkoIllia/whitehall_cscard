# Дроп-ціна + вивантаження прайсу покупцям у Google Sheet

Фіча складається з двох частин:
1. **Дроп-ціна** — друга ціна для кожного товару (для дропшиперів), похідна від наявних цін.
2. **Прайс покупцям** — вивантаження цих цін у Google-таблицю (повне перезаписування).

Гілка розробки: `feature/drop-price` (від `main`). Змін до схеми БД **немає** (жодної міграції).

---

## 1. Дроп-ціна

### Що це і як рахується

Дроп-ціна = **середина між базовою (закупівельною) і фінальною (роздрібною) ціною**, округлена вгору до 10:

```
drop = CEIL( (price_base + price_final) / 2 / 10 ) * 10
```

Це еквівалент «поділити націнку навпіл»: покупець-дропшипер отримує ціну на півдорозі між твоєю закупкою і роздробом.

**Приклади (за реальним правилом націнки #3):**

| Базова | Фінальна | Дроп |
|---:|---:|---:|
| 800 (+300 грн) | 1100 | **950** |
| 4895 (+32%) | 6470 | **5690** |
| 8000 (+20%) | 9600 | **8800** |

### Ключові властивості

- **Не налаштовується на фронті.** Немає окремого «типу націнки для дропа», полів чи override. Єдине, що керує дропом опосередковано — наявні **правила націнки** (вони формують `price_final`). Змінив правило → після наступного finalize `price_final` оновиться → дроп перерахується сам. **Одне джерело правди.**
- **Рахується на льоту** (SQL-вираз), НЕ зберігається окремою колонкою. Тому: без міграції, без backfill, без змін finalize-движка.
- Коефіцієнт `÷2` (середина) **захардкоджено** у SQL/коді. Змінити на інший (напр. 60% націнки) — невелика правка (у майбутньому можна винести в `markup_settings`).
- Дроп завжди **між** базовою і фінальною (перевірено на всій прод-базі: жодного `drop < cost` чи `drop > retail`).

### Де показується

| Місце | Що |
|---|---|
| Адмінка → **Дані → Фінальні товари** | колонка «Дроп ціна» ([DataTab.jsx](../frontend/src/tabs/DataTab.jsx)) |
| **CSV** «Скачати CSV» на тому ж вигляді | стовпець `price_drop` (у кінці рядка) |
| Google-таблиця «Прайс покупцям» | колонка «Ціна» (див. нижче) |

**Куди дроп НЕ потрапляє:** у магазин CS-Cart (туди й далі йде `price_final`), у вигляди «Порівняння / В магазині / До відправки», у merged/raw. Дроп повністю ізольований від пушу в магазин.

Реалізація: обчислюваний стовпець у `CatalogAdminService.listFinalPreview` (роут `/admin/api/final-preview` + CSV `/admin/api/final-export`).

## 2. Прайс покупцям (Google Sheet)

### Колонки таблиці

`Артикул | Назва | Розмір | Кількість | Ціна(дроп)` — один рядок на `(артикул, розмір)`, тільки товари **в наявності** (`quantity > 0`).

Згори — **виділений банер** «Прайс актуальний станом на DD.MM.YYYY, HH:MM (Київ)» (злитий по ширині, жовтий, жирний). Час = **завершення останнього finalize** (не час запису), у київському поясі. Верхні 2 рядки заморожені.

### Як і коли оновлюється (подієва модель)

Вивантаження **прив'язане до події завершення `finalize`**, а не до окремого часу:

```
крон → update_pipeline:
   mirror_sync → import_all → finalize ──▶ [прайс покупцям: DETACHED, свій лок + таймаут]
                                              │  (помилка → лише warning у лог)
                                              ▼
                                          store_import (CS-Cart, як було)
```

- **Слідує за будь-яким кроном.** Зміниш розклад `update_pipeline` — прайс іде за ним автоматично, окремого крона немає.
- **Затримка пайплайну не страшна** — це крок у ланцюжку, завжди після finalize, без гонки по часу.
- **DETACHED (fire-and-forget):** запускається після finalize й одразу віддає керування далі — **не затримує `store_import`** (пуш у магазин) і **не може завалити/заблокувати** пайплайн.
- **Толерантність:** збій/таймаут запису в Google → лише `warning` у лог; пайплайн і магазин оновлюються як завжди.

Крім авто — є **ручна кнопка** «Вивантажити прайс покупцям (Google)» у вкладці **Ручне керування** (той самий сервіс).

### Повне перезаписування (без дублів)

Перед кожним записом — `values.clear` на всю вкладку, потім банер+шапка+дані наново. Тож дані **завжди свіжі**, без лишків від попереднього прогону і без дублів (`products_final` і так дедуплікований `DISTINCT ON (article,size)` на finalize).

### Захист і стабільність

- **Свій лок `buyer_price_export`** (таблиця `job_locks`): другий одночасний запуск → `status: locked`, пропускається. Цей тип **не** в `BLOCKING_JOB_TYPES`, тож не блокує пайплайн.
- **Хард-таймаут** (`Promise.race`, дефолт 180с) — завислий Google не тримає нічого вічно; фолбек 180с при невалідному env.
- **Власний rate-limiter** у writer'і (окремий від імпорт-шляху) — бекоф запису не морозить планові імпорти прайсів постачальників. Читання і запис у Google — різні квоти.
- **Пакетний запис** ~10k рядків/виклик → 130k = ~15 викликів (квота 60/хв — з великим запасом).

### Читання даних

`BuyerPriceExportService` читає `products_final (quantity>0)` **keyset-порціями** (по `id`, без OFFSET) — лише `SELECT` (ACCESS SHARE), що **не конфліктує** з finalize (RowExclusive), тож базу не блокує. ~148k рядків × 5 колонок ≈ десятки МБ у пам'яті на час прогону.

## 3. Конфіг (env)

| Змінна | Дефолт | Призначення |
|---|---|---|
| `BUYER_PRICE_SHEET_ID` | — | ID/URL цільової таблиці. **Обов'язково** для роботи (кнопки й авто) |
| `BUYER_PRICE_SHEET_TAB` | `Прайс` | Назва бойової вкладки |
| `BUYER_PRICE_EXPORT_ENABLED` | `false` | `true` = АВТО-крок після finalize. **Кнопка/CLI працюють і без нього**, аби був `SHEET_ID` |
| `BUYER_PRICE_BATCH_ROWS` | `10000` | Рядків на один запис у Google |
| `BUYER_PRICE_TIMEOUT_MS` | `180000` | Хард-таймаут запису |

`GOOGLE_CLIENT_EMAIL` + `GOOGLE_PRIVATE_KEY` — **вже є на проді** (writer реюзає їх зі scope read/write). Сервіс-акаунт `GOOGLE_CLIENT_EMAIL` має бути **Редактором** цільової таблиці.

`BUYER_PRICE_EXPORT_ENABLED` гейтить **лише авто-крок**; ручна кнопка залежить лише від `BUYER_PRICE_SHEET_ID` (`isConfigured()`), авто — від `isAutoEnabled() = enabled && configured`.

## 4. CLI (пре-флайт / ручний запуск)

```bash
# синтетичний семпл (без БД, лише Google-креди + editor-доступ):
node dist/scripts/runBuyerPriceExport.js --sample --sheet <ID> --tab DRAFT
node dist/scripts/runBuyerPriceExport.js --sample --dry-run       # тільки друк, без запису

# реальні дані з products_final (читає DATABASE_URL):
node dist/scripts/runBuyerPriceExport.js --real --sheet <ID> --tab DRAFT
```

Через npm (підвантажує `.env`): `npm run export:buyer-price -- --sample --tab DRAFT`.

**Пре-флайт на проді:** `--real --tab DRAFT` пише реальні 148k у чернеткову вкладку (read-only для БД) — замір часу/квоти перед вмиканням авто.

## 5. Безпека / ізоляція (чому не ламає прод)

- Зміни **адитивні**. Єдиний дотик до прод-пайплайну (`update_pipeline`) гейтований `isAutoEnabled()` (**OFF за замовч.**) і **detached** — фізично не може заблокувати/затримати/завалити пайплайн чи пуш у магазин.
- При невиставленому `BUYER_PRICE_*` env — поведінка пайплайну **байт-у-байт як була**.
- Дроп у CSV — **у кінці** рядка (не зсуває індекси наявних колонок).
- Змін до схеми БД немає (тип job `buyer_price_export` — вільний TEXT).

### Перевірено

- typecheck + build + frontend build — зелені;
- дроп-формула валідована на **всіх 148 392** прод-рядках (0 аномалій);
- інтеграційний тест `BuyerPriceExportService` на реальному Postgres: `quantity>0` фільтр, дроп-значення, NULL розмір/назва→порожньо, банер=час finalize (TZ Київ), порожній датасет без падіння, лок→`locked`, locked-скіп→`failed` (не orphan).
